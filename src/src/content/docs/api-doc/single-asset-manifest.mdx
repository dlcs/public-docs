<Aside type="caution">
  The single asset manifest does not yet represent in IIIF everything the platform knows about your asset and all the services and adjuncts it can offer.
</Aside>

For every asset there is a _single asset manifest_: a IIIF Presentation 3.0 Manifest that includes all the outputs of all the delivery channels specified for the asset.

This manifest has one canvas, with a single painting annotation — unless the asset has nothing to paint. An asset with no delivery channels, or an `iiif-av` asset with no transcoded outputs, produces a manifest with no canvas at all (see the examples below).

If the asset is an image, audio or video, the canvas dimensions are taken from the source asset. Otherwise, the canvas dimensions are set to width = 1000, height = 1000, with no duration.

The `id`s of the canvas, its annotation page and its painting annotation are minted under the `/iiif-img/` path prefix for every asset type — audio, video and file-only assets included. They are identifiers, not links.

The single asset manifest is a public IIIF resource served by the platform, not the API - no API credentials are required.

```
{public-host}/iiif-manifest/{customer}/{space}/{asset-id}
```

The manifest is served as IIIF Presentation 3.0 by default. A Presentation 2.1 version is available by inserting an optional version segment:

```
{public-host}/iiif-manifest/v2/{customer}/{space}/{asset-id}
{public-host}/iiif-manifest/v3/{customer}/{space}/{asset-id}
```

The unversioned URL also supports content negotiation — name the desired Presentation context in the `Accept` header, as described for [named query projections](../named-queries#iiif-resource-versions). All the examples on this page are Presentation 3.

- For the `iiif-img` delivery channel, the body of the painting annotation is a full/max parameterisation of the v3 image service, with that image service as a `service` property of the body image.
- For the `iiif-av` delivery channel, the body of the painting annotation is the transcoded output itself (a `Sound` or `Video` Content Resource) when there is a single transcode, or a `Choice` resource listing all the transcoded outputs when there are several. Each output is a Content Resource whose `id` is the parameterised path of that transcode, with `format` (the transcode's media type) and its width, height and/or duration; no `label` is generated. An `iiif-av` asset with **no** transcoded outputs gets no canvas in the manifest at all — even if it also has the `file` delivery channel.
- If the asset is an image and _does not have_ the `iiif-img` delivery channel but does have the `thumbs` delivery channel, the body of the painting annotation is a full/max parameterisation of the v3 _thumbnail_ image service.

If the asset has the `iiif-img` delivery channel, the body of the painting annotation has two services, one for v2 and one for v3 of the Image API. If the asset has access control, the auth services are included inline on the image services.

If the asset has the `thumbs` delivery channel, the `canvas.thumbnail` property is an image resource whose `id` is the full/max parameterisation of the v3 thumbnail image service. This image resource has v2 and v3 thumbnail services.

The output of the `file` delivery channel is always available as `canvas.rendering`, with auth services emitted inline if applicable.

If the asset _only_ has the `file` delivery channel, the body of the canvas painting annotation is a placeholder image provided by the platform, served from `{public-host}/static/{type}/placeholder.png` (where `{type}` reflects the asset's media type, e.g. `text`). The canvas is then given the additional `placeholder` behavior, and the rendering is given the additional behavior `original`. These behavior values come from the born-digital extension, and the manifest's `@context` becomes an array that includes the extension context `https://iiif.wellcomecollection.org/extensions/born-digital/context.json`.

Any [adjuncts](../adjuncts) with an `iiifLink` value are expressed under the corresponding IIIF Canvas properties (`seeAlso`, `rendering`, `annotations`, or as inline annotations).

## Examples

The following examples show complete IIIF Presentation 3 Manifests for various asset, delivery channel and adjunct combinations. All of them are taken from real platform output, with only the hostname, customer, space and asset identifiers substituted.

### Image with iiif-img and thumbs

An image asset registered with both `iiif-img` and `thumbs` delivery channels. The manifest carries a `thumbnail` at the top level (using the platform's medium thumbnail size) and a `label` and `metadata`. The canvas carries the same `thumbnail` and its own `metadata` block reflecting the asset's string, number, tag and role fields. ### Video with iiif-av

A video asset on the `iiif-av` delivery channel, with a policy specifying two transcoded outputs — an MP4 and a WebM. The canvas has `width`, `height` and `duration`, taken from the transcodes. The painting body is a `Choice` wrapping the two outputs; each output's `id` is its parameterised path, ending in the container's file extension.

<Aside type="caution">
For a `Choice` to be useful, each output in the policy must use a **different container format** (e.g. one MP4 and one WebM). The storage location of a transcode is currently distinguished only by file extension, so two outputs sharing a container overwrite each other, and the `Choice` presents them with identical `id`s. This is tracked in [protagonist #970](https://github.com/dlcs/protagonist/issues/970).
</Aside>

The canvas defaults to 1000×1000 and is given `behavior: ["placeholder"]`. The painting body is a placeholder image provided by the platform.
